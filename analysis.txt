Benchmark Analysis

Across all tested dataset sizes and distributions, Linear regression had the lowest overall mean creation time (7.27 ms); SQLite B-tree had the lowest overall mean random search time (1.52 µs); Linear regression had the lowest overall mean range search time (72.72 µs). These are averages across the experiments, so results can vary by data type and size. 
At the largest tested size, at 1,000,000 records, Linear regression was fastest for creation (23.76 ms); at 1,000,000 records, SQLite B-tree was fastest for random search (1.74 µs); at 1,000,000 records, Linear regression was fastest for range search (68.42 µs). Creation time includes the work performed by each implementation: SQLite row insertion plus index creation for the B-tree, and model training plus calibration for learned indexes. These timings are therefore implementation-level comparisons, not isolated algorithm costs.

Distribution-specific results were: For linear data, the lowest average times were creation: Linear regression, random search: SQLite B-tree, range search: Neural network; For skewed data, the lowest average times were creation: Linear regression, random search: SQLite B-tree, range search: Linear regression; For temporal data, the lowest average times were creation: Linear regression, random search: SQLite B-tree, range search: Linear regression. The charts should be used to inspect whether a model’s performance changes on skewed or temporal keys; learned-index prediction quality depends on how well the key-to-position relationship is modeled. Across sizes, SQLite B-tree creation changed from 1.18 ms at 1,000 records to 794.90 ms at 1,000,000; Linear regression creation changed from 1.38 ms at 1,000 records to 23.76 ms at 1,000,000; Neural network creation changed from 47.20 ms at 1,000 records to 861.09 ms at 1,000,000; SQLite B-tree random search changed from 1.33 µs at 1,000 records to 1.74 µs at 1,000,000; Linear regression random search changed from 70.20 µs at 1,000 records to 69.29 µs at 1,000,000; Neural network random search changed from 88.89 µs at 1,000 records to 81.59 µs at 1,000,000; SQLite B-tree range search changed from 45.25 µs at 1,000 records to 50.63 ms at 1,000,000; Linear regression range search changed from 67.41 µs at 1,000 records to 68.42 µs at 1,000,000; Neural network range search changed from 81.33 µs at 1,000 records to 82.75 µs at 1,000,000.

The main trade-off is that a B-tree provides general-purpose ordered lookup and range-query support without needing the key distribution to follow a learned pattern. A learned index can narrow a search when key positions are predictable, but it adds model-training and calibration costs, consumes model resources, and may need rebuilding when data changes. In this benchmark, learned-index lookups also use a binary-search fallback for correctness. I would recommend a B-tree for frequently updated data, unpredictable distributions, and dependable range queries. I would consider a learned index for mostly static, large datasets with a stable, predictable key distribution, after measuring its build and maintenance costs. 
A result worth discussing as surprising is any case where the apparently more sophisticated learned model was slower than the B-tree; model prediction overhead and training cost can outweigh search savings. Use the actual plots to identify and state your own specific surprise rather than assuming one. The B-tree baseline here is SQLite’s B-tree index, not a separately implemented B+ tree, and benchmark times depend on hardware, software versions, and system load. These limitations should be acknowledged when interpreting the results.
